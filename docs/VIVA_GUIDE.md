# DBGuard Viva & Oral Examination Defense Guide

## Computer Science & Engineering University Mini-Project

This comprehensive guide is prepared for external examiner evaluation of the mini-project:
**DBGuard — Intelligent Integrity Assessment of Compressed Database Exports Without Full Database Restoration**.

---

### Category 1: Problem Statement & Motivation

#### Q1: What is the official problem statement addressed by DBGuard?
**Answer:** The project investigates a real-world production anomaly where a compressed database export experienced a 30% increase in row count compared to an earlier export, yet the compressed file size unexpectedly decreased by 20%. Management suspected the backup was corrupted and unrecoverable. Because the database was very large, there was neither time scope nor tablespace scope to test-restore the backup into a secondary scratch database. DBGuard was created to assess the physical and logical integrity of such archives in bounded RAM without restoration.
*Examiner Tip:* Highlight that decompressing or restoring terabyte-scale dumps consumes excessive IOPS and temporary disk space.

#### Q2: Why is restoring a database into a temporary database undesirable or impossible in enterprise environments?
**Answer:** 
1. **Tablespace Constraints:** Provisioning hundreds of gigabytes or terabytes of high-performance SSD storage just to validate a periodic backup creates massive infrastructure cost.
2. **Time Window (RTO):** Full database restoration from a large dump involves index rebuilding, table creation, and transaction log replay, often taking 12 to 36 hours.
3. **I/O Contention:** Restoring large volumes generates heavy disk read/write load that can degrade performance on active database servers.
*Examiner Tip:* Use industry terms like "Recovery Time Objective (RTO)", "IOPS saturation", and "scratch tablespace depletion".

#### Q3: Does a smaller compressed file automatically imply data loss or corruption?
**Answer:** No. Compression algorithms (like DEFLATE, Bzip2, LZMA) compress data based on redundancy and Shannon information entropy, not row counts. If new rows contain repeated values (e.g. repeated default status codes, identical foreign keys), shorter text fields, or a high ratio of NULL columns, the compressed file can legitimately be substantially smaller despite containing more records.
*Examiner Tip:* Quote Shannon's Source Coding Theorem: entropy determines the lower bound on compression size.

#### Q4: What are the three decoupled verification layers in DBGuard?
**Answer:** 
- **Layer 1: Physical Stream Integrity:** Verifies container headers, magic signatures, block bitstreams, and CRC32/Adler32/CRC64 container checksums.
- **Layer 2: Structural & Syntactic Integrity:** Tokenizes the uncompressed stream to verify record delimiters, unescaped quote invariants, column count consistency, and schema structural fingerprints.
- **Layer 3: Provenance & Logical Completeness:** Reconciles the observed dump against an independent export manifest generated by the source database export pipeline.
*Examiner Tip:* Emphasize that decompressing cleanly (Layer 1) does NOT prove completeness (Layer 3).

#### Q5: Can computing a SHA-256 hash on an export file prove it contains all source rows?
**Answer:** No. A hash computed after the fact only proves that the file hasn't changed since that hash was calculated. If the database export command prematurely terminated or skipped rows due to an error, a post-hoc SHA-256 will faithfully hash an incomplete file. Only an independent manifest generated at export time by the database engine can certify completeness.

### Category 2: Compression & Anomaly Detection

#### Q6: How does the DEFLATE compression algorithm work?
**Answer:** DEFLATE is a combination of LZ77 (Lempel-Ziv 1977 dictionary compression) and Huffman entropy coding. LZ77 searches for duplicate byte strings in a sliding window (typically 32 KB) and replaces matches with (length, distance) pointers. Huffman coding then assigns shorter variable-length bit codes to frequent literal bytes and pointers.

#### Q7: How does DBGuard detect stream truncation in gzip files?
**Answer:** Standard gzip (RFC 1952) mandates an 8-byte trailer at the end of the DEFLATE stream containing:
1. `CRC32` (4 bytes): The cyclic redundancy check of the uncompressed data.
2. `ISIZE` (4 bytes): The uncompressed data size modulo $2^{32}$.
DBGuard reads to the container end, verifies that the stream terminates cleanly with the trailer, and compares the running stream CRC-32 against the trailer value.

#### Q8: What is a compression bomb (zip bomb) and how does DBGuard mitigate it?
**Answer:** A zip bomb is an archive engineered to expand to gigantic sizes from a minuscule file (e.g. 42 KB expanding to 4.5 petabytes). DBGuard mitigates this by:
1. Tracking the expansion ratio continuously in streaming mode.
2. Terminating processing if the expansion ratio exceeds safety limits (e.g., 1000:1) or decompressed bytes exceed configured bounds.

#### Q9: What is the "Bytes-Per-Record" metric and how did it diagnose the official paradox?
**Answer:** Bytes-per-record is $\frac{\text{Total Decompressed Bytes}}{\text{Total Rows}}$. In the 30% row increase / 20% size decrease case, bytes-per-record dropped from 85.2 bytes to 52.8 bytes. This proved that newly inserted rows were significantly shorter and more uniform, explaining the paradox without corruption.

#### Q10: What is Median Absolute Deviation (MAD) in DBGuard's anomaly detection?
**Answer:** When evaluating an export against historical backup baselines, simple standard deviation ($3\sigma$) can be skewed by historical outliers. Median Absolute Deviation (MAD) is a robust statistical measure:
$$\text{MAD} = \text{median}(|X_i - \text{median}(X)|)$$
It detects anomalous shifts in row size or compression ratios with high resilience against historical noise.

### Category 3: Streaming Architecture & Bounded Memory

#### Q11: What is bounded-memory streaming and what is DBGuard's space complexity?
**Answer:** DBGuard has $O(B)$ space complexity, where $B$ is a fixed 64 KB chunk size. It never loads the whole compressed file or the full uncompressed dataset into RAM. Resident set size (RSS) RAM stays under 2 MB regardless of whether the dump is 100 MB or 100 GB.

#### Q12: How does DBGuard stream-parse CSV data without writing uncompressed files to disk?
**Answer:** DBGuard implements `ChunkGeneratorReader` (in `dbguard/stream/reader.py`), a custom `io.RawIOBase` adapter that wraps a generator yielding decompressed chunks. Standard Python text readers and `csv.reader` consume directly from this memory adapter.

#### Q13: What is "Single-Pass Stream Tapping"?
**Answer:** In single-pass stream tapping, each chunk emitted by the decompressor is simultaneously routed to:
1. The whole-file uncompressed SHA-256 hasher.
2. The 1 MB chunk boundary hasher and Merkle tree leaf builder.
3. The streaming row tokenizer and column analyzer.
This eliminates duplicate disk reads or multiple passes.

#### Q14: How does DBGuard handle malformed records or quotes?
**Answer:** If an unclosed quote, invalid UTF-8 byte, or mismatched column count occurs, DBGuard records the error, logs the byte offset, increments `malformed_rows`, and continues scanning remaining records to compute the recoverable row count estimate.

#### Q15: What is the time complexity of DBGuard?
**Answer:** The time complexity is $O(N)$ where $N$ is the byte size of the export, because decompression, SHA-256 hashing, and delimited row parsing all execute in linear time in a single pass.

### Category 4: Cryptographic Hashing & Manifests

#### Q16: Why does DBGuard use Chunk Hashes and Merkle Trees in addition to a whole-file SHA-256?
**Answer:** A whole-file SHA-256 is all-or-nothing: if 1 bit fails, the whole hash mismatches, but you cannot determine where the failure occurred. DBGuard hashes 1 MB chunk boundaries into a Merkle Tree. This pinpoints the exact 1 MB segment containing corruption, allowing DBAs to salvage clean blocks.

#### Q17: What is a Schema Fingerprint in DBGuard?
**Answer:** A schema fingerprint is a SHA-256 digest of the canonical column names and inferred types:
$$\text{Fingerprint} = \text{SHA-256}(\text{"col1:type1|col2:type2|..."})$$
It flags schema drift between backup cycles.

#### Q18: What is HMAC authentication in DBGuard manifests?
**Answer:** HMAC-SHA256 signs the manifest with a shared secret key. This guarantees tamper resistance: an attacker or corrupted backup script cannot modify both the dump and the manifest without possessing the secret key.

#### Q19: What are the 6 recovery classifications?
**Answer:**
1. `VERIFIED_WITHIN_SCOPE`: All stream checks pass and trusted manifest matches.
2. `LIKELY_USABLE_BUT_NOT_FULLY_VERIFIED`: Stream and rows are valid, but no manifest exists to prove 100% source completeness.
3. `RECOVERY_POSSIBLE_WITH_ERRORS`: Partial truncation or corrupt lines detected, but preceding blocks are salvageable.
4. `INTEGRITY_FAILURE`: Bad CRC checksum, unreadable container, fatal abort.
5. `INCONCLUSIVE`: Ambiguous anomaly requiring comparative analysis.
6. `UNSUPPORTED_FORMAT`: File container not recognized.

### Category 5: Full-Stack Engineering

#### Q20: Describe the full-stack architecture of DBGuard.
**Answer:**
- **Frontend:** React 18, TypeScript, Vite, Tailwind CSS, Lucide icons, Recharts for visual analytics.
- **Backend:** FastAPI (Python 3.12), Pydantic v2 schemas, SQLAlchemy ORM with SQLite for analysis records and benchmarks.
- **Engine:** Python standard library (`gzip`, `bz2`, `lzma`, `hashlib`, `csv`, `io`), bounded 64 KB buffers, ReportLab for PDF generation.

#### Q21: How are large file uploads handled without memory exhaustion in FastAPI?
**Answer:** FastAPI utilizes Starlette's `UploadFile`, which automatically spools files larger than 1 MB into temporary disk files. The streaming engine then opens these files in 64 KB chunks, preserving bounded server RAM.

#### Q22: How does the comparator route (`/api/comparisons`) function?
**Answer:** It streams both the baseline and candidate files simultaneously, extracts row counts, compressed sizes, and decompressed sizes, evaluates schema compatibility, and executes anomaly rules such as negative size divergence.
